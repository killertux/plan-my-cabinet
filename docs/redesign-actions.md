# Desktop action inventory before workspace relocation

Task 4.1 baseline: these are the actual controls in the single scrolling sidebar and its dialogs. `src/actions.rs` assigns each command a stable `ActionId`, an existing Fluent label key, English and pt-BR search terms, a destination, a typed target where needed, and an availability reason. The visible control and a future palette result call the same entry point. IDs refer to project UUIDs, not names or list positions; execution checks that a target still exists. Disabled controls can show the localized reason. `actions::tests::existing_capabilities_have_unique_accessible_localized_routes` verifies the inventory against the registry and both translation bundles.

Other existing inputs remain live controls on their owning surfaces: display units, board and stock grain choices, stock trims/quantity/source/price, repair target/coordinates/rotation, hierarchy and canvas selection, camera controls, and modal field values. Draft fields commit through their registered dialog action, retaining validation and rounding consent. The viewport's camera/tool controls remain in `viewport::show_move`; view-only changes do not create project transactions. Routes name their intended workspace, while every listed control is currently reachable in the existing single-sidebar application.

Availability is evaluated again at activation. Missing UUIDs, modal or picker isolation, missing selection/material/second board, undo/redo emptiness, stock priority endpoints, reference-hardware-only editing, invalid motion, repair state and export readiness produce explicit bilingual reasons. Contextual session/form commands use `actions::contextual`/`actions::decision`, with the active controller supplying its stricter validation; this preserves source revision and rounding-consent checks instead of routing around them.
