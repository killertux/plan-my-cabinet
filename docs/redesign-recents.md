# App-local recent projects

`RecentProjects::open(absolute_user_data_dir)` reads `recent-projects.json` from the platform application user-data directory. The caller must supply that directory; no current-directory or project-folder fallback exists. The index is versioned, bounded to 128 entries and 128 KiB, duplicate-key checked, and written by same-directory atomic replacement. Missing index means empty recents. Invalid, unsupported, oversized or unreadable indexes return an error and remain intact for diagnosis; the host should report the error rather than overwrite the index.

After the host completes a validated **open** (including unsaved-work and prepared-load guards) or an explicit **save**, call `register_successful(path, project_id, SystemTime::now())`. Do not call it for a picker selection, prepared-but-unaccepted open, cancelled/failed save, unsaved new/template project or recovery snapshot. Registration independently reads the bounded project file through `persistence::prepare_reader`, verifies its UUID, canonicalizes its path, caches its actual name/counts, and records the last successful use. The index write failure is reported separately from an already successful project operation. Reopening an alias refreshes one entry; a copy with the same UUID at a different path gets its own entry. A different UUID replacing a file at the same path supersedes that path's old identity. The index and thumbnail reference are local derived data, never portable `.pmcab` fields.

`list(filter)` revalidates each registered file, without scanning project folders or changing files. `Available(summary)` reports current name, board/assembly/material/stock and export-record counts from validated bytes, alongside a separately qualified `export_status` computed from those same validated bytes. A receipt count alone is not a claim of current Shop-ready status or a recovery decision. `Missing` and `Unavailable(reason)` carry no current metadata or export status; the entry's `cached_summary` is historical and must be labeled accordingly if displayed. Paths and last-use timestamps are index data, not a guessed project export or recovery timestamp. Recovery status belongs to `RecoveryIndex::discover`, matched by **both** canonical path and UUID. Case-insensitive filtering matches the current validated name (or explicitly historical cached name) and path.

`list` performs bounded file validation for each entry. The Welcome host should
cache its returned view until opening Welcome, a successful open/save, a
Locate/Remove action or an explicit refresh; do not call it every egui frame.

The desktop file lifecycle registers after `save_to` reports success (including
confirmed overwrite and Save As), and after a prepared open is actually accepted
and installed by `proceed(Open)`. A dirty-document prompt, cancelled picker,
declined overwrite, failed load/save, and unsaved New do not register. It uses
the same app-local `user_data_dir` as recovery, registers the saved canonical
path/UUID in `RecoveryIndex` after each accepted file operation, and reports
local index errors alongside the operation result without reverting the already
saved or opened project. The Welcome UI, list caching, Locate/Remove controls,
and thumbnail generation are separate integration work.

For a missing entry, `locate(old_canonical_path, project_id, selected_file)` validates the selected file before changing the index. A different UUID is rejected with an explicit identity error; a valid relocated/copy file of the same UUID updates the path and cached summary without claiming an additional successful open. `remove(path, id)` writes only the index; it never deletes or rewrites project, recovery, export or thumbnail files. The desktop lifecycle must still guard any eventual open with its existing unsaved-work and prepared-load checks. Thumbnail generation and Welcome integration follow separately.

## Welcome presentation component

`src/welcome_ui.rs` exports `WelcomeState { filter }` and `show(&mut self, ui: &mut egui::Ui, localizer: &Localizer, recents: &[RecentProjectView], discoveries: Option<&[RecoveryDiscovery]>) -> Vec<WelcomeIntent>`. The host supplies a full cached `RecentProjects::list("")` on entering Welcome and refreshes it after accepted open/save/Locate/Remove or explicit refresh. Filtering is entirely in-memory against the validated current name (or clearly labeled last-known cached name for invalid/missing documents) and indexed path. The component never opens files. `None` discovery means *not checked*, while `Some(&[])` means discovery completed with no registered candidate; pass `RecoveryIndex::discover()` only after successful index access. Recovery badges require both canonical path and UUID; they never infer availability from a shared name or a copied document's UUID.

The host renders `WelcomeState::show` in its native content panel (typically an `egui::CentralPanel`) and handles each returned intent: `NewProject` and `OpenProject` through existing replacement/unsaved-edit guards; `OpenProject` launches the native file picker, then prepared-load validation and guard acceptance; `OpenRecent { path, project_id }` revalidates the selected file and its UUID at activation, then uses those same guards; `Locate { path, project_id }` opens a native picker and calls `RecentProjects::locate` only after the picker returns a file, reporting its validation error without changing the active project; `Remove { path, project_id }` calls `RecentProjects::remove` only and refreshes the list; `Preferences` opens app Settings; `SetLanguage(Language)` updates the app-local preference and its `Localizer`. `recent_intent` emits no Open for missing/unavailable rows. View rendering and all intents leave project bytes and index bytes unchanged until the host explicitly acts. A host error should remain visible beside the relevant recent row after failed Locate or open.

The page uses the handoff's warm two-column composition at 1100 × 700 logical points and a vertical-scroll layout under 780 points. The recent list scrolls independently for many entries, and it shows actual validated board/assembly/material/stock counts, last successful use, a qualified export-status label, and an explicit recovery-discovery label. Invalid rows show the validation reason and no fabricated current counts or export result. Every thumbnail is a neutral placeholder until task 12.2 supplies actual offscreen saved-state captures. The template and recovery-action areas carry explicit unavailable copy rather than controls that imply generation or recovery decisions exist. Interactive template setup and recovery comparison/actions belong to tasks 13.5 and 12.4 respectively; component tests cover empty/list, long pt-BR and narrow layout, identity-qualified intents and nonmutating Locate/Remove.
